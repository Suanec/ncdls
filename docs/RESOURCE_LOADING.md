# 资源加载、离线缓存与更新

适用当前手机/PWA 构建 `20261125.5`。基础 `web-game/` 共用引擎和页面适配，但没有手机菜单及完整 PWA 缓存流程。

## 一次启动经历什么

```text
首页 HTML（内嵌提示与计时）
  → 页面先绘制 → 准备按需缓存 → 无游戏缓存时询问加载方式
  → 读取/下载运行代码 → 初始化引擎
  → 读取/下载本关配置、模型、图片等 → 解析并创建场景 → 游戏
```

当前合并运行文件约 9.3 MB，仅包含引擎与代码。当前离线清单为 1,901 文件、约 44.4 MiB，组织为 21 个传输包；这些是版本快照，后续以生成的 `offline-manifest.json` 为准。核心包到达不等于所有图片、模型已加载。

首屏不等引擎下载；iframe 和外部组件在首次页面绘制后启动。运行代码按依赖顺序执行，资源阶段按完成/待完成数量和字节反馈；未知总量不伪造百分比。读取本机缓存、网络下载、解析、场景创建分别标注。

## 首次选择与按需加载

检查本游戏目录的 Cache Storage：只有页面文件不算游戏资源；存在 `runtime/`、`res/` 或 `prefab/` 文件则跳过询问。

- **按需加载**：只加载代码及实际使用的资源，下载过的文件保存后复用；切换玩法或首次使用特效时可能补下载。
- **全部下载**：等待当前构建资源校验并保存完成，再启动游戏。失败后已完成部分保留，可重试或改选按需加载。
- 已有缓存不再询问，也不自动全量预取。游戏内的“保存离线资源 / 检查并下载更新”仍可触发完整下载。
- HTTPS / localhost 下自动注册缓存组件；普通 LAN HTTP 或存储不可用时降级在线按需运行，不承诺离线可用。

每次重新打开仍需执行 JavaScript、解析模型与图片、创建场景并上传纹理。持久缓存保存的是文件，不是运行中的引擎或盘面。

## 为什么完整下载使用资源包

原来数千个小文件逐一请求，手机网络的每次响应等待被累计放大。手机版把 15 个必需脚本合成一个文件，完整下载按包传输、按原 URL 分文件缓存；只缺少少量文件或包里只有一个文件时，直接补原文件。

传输包用 JSON/Base64，服务器可做 HTTP 压缩。页面接收量是浏览器得到的响应体大小，不等于链路实际流量；Base64 有额外体积。包解开后不另存整包，不会每次启动再解包一次。原始 Brotli 在构建时已展开；图片和引擎二进制仍要运行时解析。这样也不依赖 iOS 15 缺少的 Compression Streams 能力。

## 校验、重试与提示

`sw.js` 对清单中资源核对长度与 SHA-256，新下载内容校验通过后才交给引擎并入缓存；已有缓存用内容指纹判断能否复用。相同资源的并发请求合并。

| 情况 | 行为 |
| --- | --- |
| 正常首次缺失 | “正在下载资源”并补齐当前请求 |
| 缓存版本不匹配、下载损坏或失败重试 | “资源版本不匹配，正在更新”，重新取当前所需文件 |
| 重试仍失败 | “资源更新暂未完成”，提供保留存档的重载入口；不无限假装在下载 |
| 一般运行异常 | 玩家页给出操作提示，原错误保留在诊断/控制台，不冒充资源下载 |

资源下载最多尝试 3 次，流式传输无新数据 30 秒超时；不可流式读取时采用 120 秒完成期限。超时 Promise 负责结束等待，不能只依赖 `abort()` 回调。持续有字节的流式慢连接允许继续。下载任务的中断监控在实际任务发出后开始，避免把缓存组件准备阶段误判为卡住。

## 更新与恢复原则

- 自动检查新 Service Worker 不下载完整离线包。已有完整旧版按自己的清单继续运行，手动更新后才切换，避免混合新旧引擎和资源。
- 未变化的文件按内容指纹复用；`.5` 核心运行文件与 `.4` 相同，不因只改页面提示就重下引擎。
- URL 查询参数会被缓存匹配逻辑去除，所以 `?v=...` 不能绕开旧完整包。
- `recover.html` 是不依赖引擎、未列入离线清单的恢复入口；注销本应用旧 Service Worker 后重新导航，保留资源与存档。新版随后恢复按需缓存。
- 存档在 localStorage，资源在 Cache Storage；两者不相同。手机可能清理缓存，下载完成不代表永久保留。

操作入口见 [手机操作](MOBILE_OPERATION.md)。旧更新阻塞、1899/1901 仍差约 20% 的原因见 [故障记录](TROUBLESHOOTING.md)。
