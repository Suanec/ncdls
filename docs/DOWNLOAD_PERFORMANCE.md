# 手机下载速度与分包说明

版本：`20261124.4`，日期：2026-11-24。正式入口始终为 [https://suanec.github.io/ncdls/](https://suanec.github.io/ncdls/)。

## 为什么之前会很慢

旧下载器使用 4 路并发，逐个下载 1,915 个资源。即使很多文件只有几 KB，每个文件都要等待一次网络响应。手机连接 GitHub Pages 时，如果每次响应都慢，小文件数量会显著放大总等待。开发电脑的网络测速不能代表用户手机的网络情况。

## 当前调整

- 手机构建将必需的 15 个运行脚本按原顺序合成 1 个文件，首次启动少 14 次请求；第一关游戏 iframe 的实际资源请求从 134 次降到 120 次。
- 手动完整下载使用 21 个资源包，浏览器实测共 23 次请求（含 Service Worker 和清单），解包后仍逐文件验证 SHA-256、写入原 URL 的缓存。合并脚本后离线文件数为 1,901，总资源约 44.4 MiB。
- 下载界面显示收到的数据量及保存进度。30 秒没有收到任何数据时中断本次请求，最多尝试 3 次；持续有数据的慢下载可以继续。
- 中断后保留已校验文件；重试及升级复用已有文件。只缺少少量小文件时，直接补文件，避免重新下载整个资源包。
- 默认按需加载保持不变，自动检查更新不下载整包。只有手动点击下载或旧版的“应用更新”按钮才触发完整下载。

资源包是 JSON，二进制文件使用 Base64，传输压缩由 HTTPS 服务器处理。页面的“已接收”统计是浏览器解压后的包数据，可能大于 44.4 MiB；它不等于实际网络流量，也不是额外缓存了一套资源。包解开后只保存原文件，不保存传输包。未依赖 `DecompressionStream`，因为 [WebKit 将 Compression Streams 列为 Safari 16.4 新功能](https://webkit.org/blog/13966/webkit-features-in-safari-16-4/#compression-streams-api)，目标设备仍有 iOS 15。

## 前后对照测试

用同一批 1,901 个文件、同一台电脑、全新浏览器缓存，对每个响应注入相同的 100 ms 等待，并启用 HTTP gzip：

| 下载方式 | 请求次数 | 完整保存耗时 |
| --- | ---: | ---: |
| 旧逐文件下载器，4 路并发 | 1,903 | 51.45 秒 |
| 新分包下载器，2 路并发 | 23 | 2.55 秒 |

这是控制条件下的本地对照，证明减少请求能降低响应等待开销；不是用户手机测速，也不承诺手机能在 2.55 秒完成。GitHub Pages 连通性和实际带宽仍影响下载，资源体积没有凭空消失。

验收覆盖：第一关画面和车辆点击、完整下载后断网重开、旧离线包升级、自动更新不全量下载、重复下载复用资源、HTTP 503 和无数据超时重试、坏包不标记完成、部分缓存续传。Chrome 手机视口已检查，iOS 15 真机尚未验收。

## 手机如何使用新版

1. 关闭当前仍在慢速下载的游戏标签页，重新用 Safari 打开固定入口。
2. 点“离线与存档 → 检查并下载更新”（首次可能显示“保存离线资源”）。旧版页面也会获取新版下载组件。
3. 保持页面在前台。新版界面显示“下载资源包”；旧界面仍可能显示逐文件计数，但收到一个包后计数会成批前进。
4. 完成后点“应用更新并重启游戏”，在“选择关卡”里确认 `20261124.4`。

不需要清除网站数据；清除会丢掉已下载资源，且可能删除存档。如果换成蜂窝网络或另一条 Wi-Fi 明显改善，说明当前网络到 GitHub 的连接也在影响速度。完全无法连接 GitHub 的网络无法单靠前端代码修好，需要可访问的静态托管；本次未迁移域名或引入第三方下载代理。
