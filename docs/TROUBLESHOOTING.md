# 故障、踩坑与验证边界

以 `20261125.5` 为当前代码基准。这里保留问题、证据、无效尝试和最终处理；历史报告中的“当前版本”“尚未修复”只代表当时，不能覆盖本文结论。

## 1. 从缓存拿到文件，却不能直接运行

缓存按需产生，未打开的玩法或房间可能没有资源；声明分包之外还有资源索引中的远程分组。某些 `.json` 实际是 Brotli，脚本又带微信模块包装、插件和平台接口。

处理：原包保留，源码分层整理，恢复模块顺序和引擎依赖，构建时解压资源，另做索引引用检查。猫咪、打巨龙、房间仍有缺口；详见 [工程还原](RESTORATION.md)。不能因分包存在就宣布游戏完整。

## 2. 按钮、螺丝板只显示碎片

共享框架覆盖了 Laya 的 `Texture.create`，另一套 WASM 裁图路径与当前缓存引擎不匹配，曾把 50×59 图集区域变成 5×11。

处理：浏览器适配保留当前引擎自己的裁图方法。文件哈希正确不代表运行库间的格式/内存布局兼容；此问题与后面的对象池重复借出不同。

## 3. 漏车、重叠、车位缺失

手机和电脑均有现象；手机访问本地服务也异常，因此不能只归因于 GitHub 或 iOS。

**失败尝试**：`20261124.1` 强制 WebGL 1，用户反馈更慢且仍错；`.2` 撤回。全局关闭合批也没有足够证据，未保留。引用浏览器兼容资料只能形成假设，不能代替复现。

**确认证据**：线上第一关黄车与绿车曾共用 `sp3.id=1827`，坐标也被覆盖；对象池返回节点后仍把它留在空闲集合，后续借用拿到同一对象，车位同样受影响。

**修复**：`20261124.3` 在 `src/shared/W.js` 的 `gO()` 返回实例前登记借出：移出空闲集合，加入使用集合；保留正常回收和共享纹理/材质。第一关恢复 4 个独立车辆实例、7 个独立车位，真实点击与重启/离线重开通过。

证据：[修复前](../reports/first-level-before.png)、[修复后](../reports/first-level-after.png)、[第一关验证](../reports/first-level-verification.json)。用户后来确认手机画面正确。历史第 100 关漏车未单独留下完整视觉复测，第一关成功不等于逐关通过。

## 4. 手机半小时下不完、页面像死机

旧完整下载逐项请求近两千文件，小文件的网络等待开销很高；首屏又依赖大运行包到达，用户看不到进展。

处理：`20261124.4` 合并运行脚本和完整下载包；`.5` 先绘制内嵌进度页，再下载运行代码。相同本地条件、每响应增加 100 ms 延迟的实验中，请求数由 1,903 降到 23，完整保存由 51.45 秒降至 2.55 秒。实际 Mac 到线上一次约 199 秒；都不是手机测速保证。用户反馈后续手机加载明显改善。

证据：[对照实验](../reports/download-benchmark.json)、[线上下载](../reports/download-live-verification.json)、[首屏](../reports/startup-verification.json)。历史上还出现“运行时初始化完成但加载画面不退出”，当时未捕获完整触发链，不能单凭加进度条就宣布根因解决。

## 5. 更新停在 80%，加版本号仍是旧版

版本 `20261124.6` 为诊断接口改动了合并运行包：虽已保存 1899/1901 个文件，剩下约 9.3 MB 大文件仍占约 20% 字节。百分比按字节，不按文件数。旧 Service Worker 忽略查询参数，所以 `?v=...` 仍命中旧版。

处理：`20261124.7` 从已有变量读取诊断，避免不必要的引擎变更；补齐无视 abort 时的超时退出、重试、非流式期限、下载线程中断后的按钮恢复；增加独立 `recover.html`。后续按需缓存继续复用旧文件。不能靠改 URL 版本号控制离线版本。

证据：[Chrome](../reports/update-recovery-chrome.json)、[WebKit](../reports/update-recovery-webkit.json)。真机当时停在 0 MB 的完整网络原因没有日志，不能把所有慢下载都归为同一 bug。

## 6. 每次进入都像在下载

旧版只为手动完整下载注册缓存，普通游玩依赖 HTTP 缓存；开发服务器还设置 no-store。界面把读取缓存也标成下载，混淆了网络与初始化。

处理：`20261125.1` 起自动按需缓存，之后区分缓存/网络来源与解析阶段；首次全量选择加入于 `.5`。已下载资源可复用，但每次仍要执行引擎、解析与建场景。见 [资源加载](RESOURCE_LOADING.md)。

## 7. 玩一会儿掉帧，车辆和卡片一起停住

早期怀疑息屏恢复，用户随后确认连续点击也会发生，第 2/294 关均遇到。`20261124.7` 真机记录确认页面可见、WebGL 未丢失，绘制却长期关闭。`20261125.1` 每帧恢复绘制只缓解症状；用户仍报告冻结。

`20261125.2` 精简诊断后，真机摘要约 11 FPS、执行 P95 87 ms，停绘 51 次/恢复 50 次，并给出关闭绘制的代码位置。后续摘要系统为 iOS 18.7，早期设备信息为 iPhone 13 Pro Max/iOS 15，不混作同一次环境。

**根因**：旧共享框架对象池维护末尾调用平台检查 `i.j(0)`。普通网页来源在约第 301 帧后增加额外计算/场景操作，第 901 帧后反复关闭绘制。本地普通来源、不点击车辆也复现了先变慢后停绘。

**修复**：`20261125.3` 的 `scripts/web-runtime-compat.cjs` 只去掉网页不适用的检查，保留对象池维护，并校验转换锚点。修复后 Chrome/WebKit 第 2/294 关运行超过 2,000 帧，无重复停绘。用户明确确认“不再卡死，也不卡顿”。

教训：把开关反复改回 true 不是根因修复；需要记录“谁关闭它”和完整帧耗时。引擎计时器推进也不意味着 3D 场景、物理和画面都在更新。

证据：[未修复基线](../reports/platform-freeze-baseline.json)、[Chrome](../reports/platform-freeze-chrome.json)、[WebKit](../reports/platform-freeze-webkit.json)。不据此承诺所有设备固定 60/120 FPS。

## 8. Failed to start the audio device

`AudioContext.resume()` 拒绝未被接住，音频恢复失败被全局异常处理误当游戏加载失败。`20261125.3` 在恢复调用点处理同步/异步拒绝，保留音频警告，下一次点击可重试；不因此重开关卡，也不吞掉其他运行错误。

## 9. 资源未齐、等待很久，最后空引用

用户截图包含 `this._displayObject.size`。FairyGUI 对象销毁后该字段为空；已在 WebKit 复现同类销毁后尺寸更新异常，但没有拿到截图原始调用栈，不能断言原事件就是某个资源缺失。

`20261125.5` 分两条处理：资源经校验后才进入引擎，坏文件自动重下并显示“资源版本不匹配，正在更新”；已销毁对象的尺寸更新与加载进度回调做生命周期保护。一般异常仍保留诊断，不能只把空引用文本换成“正在下载”后无限等待。

实际浏览器验证了损坏图片一次后重下成功、首次两种加载方式、缓存重开和销毁对象保护；`.5` 这条截图触发链尚无新增真机复测结论。见 [资源测试](../reports/resource-loading-webkit.json)。

## 10. 关卡、道具与显示数据容易误读

- 515 是所有玩法配置条数，393 是当前网页五种玩法模板总数，294 是经典模板数；不是同一个上限。
- 原版跳过循环后的教学模板，294 后显示 296；网页版 `.4` 已改成 294 → 295 → 296。
- “无限磁铁/刷新”保留动画和目标条件，按钮一直为 1 不等于随时能成功使用。
- “超过 99% 用户”由耗时区间随机生成，不是服务器排行。
- 普通装车与磁铁选车优先级不同；“画面有空孔”也不等于没有在途螺丝。用户所述两辆同色车都没走，没有留存对应现场，不能直接判定为随机规则或已修复 bug。

具体机制见 [玩法实现](GAMEPLAY_LOGIC.md)。

## 11. 如何读诊断、保留证据

冻结先保留现场，再“选择关卡 → 检测卡顿 → 复制诊断摘要”；不要先重开。摘要不超过 600 字，完整 JSON 可导出，不会自动上传。

| 数据 | 含义与边界 |
| --- | --- |
| 父页面帧、引擎帧、末帧距今 | 区分整个页面停顿和游戏内部停顿；还需结合暂停、可见性与对象位置 |
| FPS、P95/最长帧间隔 | 平均流畅度和偶发长帧；平均高也可能卡顿 |
| 整帧执行 P95/最长 | 主线程成本，不是 GPU 完成时间；旧报告只测 Stage.render 的数据不能直接比较 |
| 绘制开关、GL 丢失、恢复/停绘次数 | 区分关闭绘制、上下文丢失和恢复循环，结合来源栈定位 |
| fast/低帧开关、画布/DPR | 配置和负载线索，不直接证明硬件不足 |

确认过的回归、故障注入、用户真机反馈要分别记录。关卡有对象、没有 JS 错误、静态哈希通过，都不能单独证明画面正确；部署成功也不等于手机已应用新版。
