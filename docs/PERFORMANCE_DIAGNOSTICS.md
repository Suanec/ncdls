# 精简诊断、掉帧与冻结

版本：20261125.2；日期：2026-11-25。

## 用户操作

- 掉帧时：正常玩约十秒，再打开“选择关卡 → 检测卡顿（保留现场）→ 复制诊断摘要”。
- 冻结时：先不要刷新或切关，直接做上述检测。
- 默认复制不超过 600 字，通常约 250 字。完整 JSON 保留在内存，可选择“导出完整诊断文件（可选）”；不会自动上传。
- 更新后应显示版本 `20261125.2`。已有旧离线版可手动更新，或使用 `recover.html` 进入当前版本，保留存档和缓存；更新会回到本关开头。

## 摘要包含什么

1. 版本、玩法、关卡、系统简写。
2. 游戏阶段、暂停、页面/引擎可见性、绘制开关、WebGL 中断状态。
3. 打开菜单前最多十秒的引擎帧率（长时间冻结后仍保留最后一段运行窗口）、父页面动画帧率、超过 50 ms 的帧间隔数。
4. 帧间隔 P95/最大值，以及引擎主线程整帧执行耗时 P95/最大值。P95 表示约 95% 的样本不超过该值，最大值用于观察偶发卡顿。
5. 检测一秒内帧数变化、最后一帧距今多久、绘制自动恢复次数和关闭次数。
6. 帧率配置、低帧开关、实际画布大小/DPR，以及车辆/卡片运动计数、触摸和错误。

采样使用固定容量数值缓冲，统计与排序只在打开菜单、点击检测时执行。W 框架会在启动时覆盖 Stage._loop，因此整帧计时在其首帧出现后安装，覆盖场景绘制、计时器和 W.Fl 任务队列；不会额外驱动帧循环。关闭绘制的调用栈限频记录，摘要只保留短位置，文件保留完整记录。

## 如何区分原因

- 配置是 `slow` 或低帧开关为 1：原游戏设置了隔帧更新；`fast` 只是跟随浏览器动画帧，不保证设备一定达到 60/120 FPS。
- 平均帧率较低且整帧执行耗时很高：需要检查引擎主线程中的逻辑、物理、场景提交和任务队列。
- 平均帧率接近 60 但最长间隔达 100 ms 以上：仍会有明显的瞬间停顿，不能仅凭平均 FPS 判断流畅。
- 引擎帧不增加而父页面帧仍推进：更像引擎循环或游戏状态停住，需要结合错误、暂停、绘制标志、最后一帧和调用来源。
- 间隔很长、引擎执行耗时却不高：可能涉及 GPU、浏览器调度或引擎帧函数之外的 JavaScript，单靠这组数字不能判定是手机性能不足。

计时只测主线程，不是 GPU 完成时间。用户此前的 iOS 15 日志是 `fast`，所以没有证据把现有问题归因于低帧设置。也没有修改默认画质、物理参数或帧率开关，以免在缺少真机测量时引入新的玩法偏差。

## 本机调查与验证边界

macOS WebKit、428×879 手机视口、DPR 3 下，第 2、294 关分别点击 11 次，整体约 60 FPS；画布为 1218×2637。第 2 关观测到一次 168 ms 长帧，第 294 关最长 32 ms。单次测量不能确定长帧根因，不能代表 iPhone 13 Pro Max / iOS 15 的实际帧率。报告中的旧 `cpu95` 测的是 Stage.render 部分耗时；新版诊断测的是完整引擎帧函数，两者范围不同，不能直接比较。

诊断回归通过人工加入长帧和停止引擎循环，验证摘要识别、场景保留、复制降级和完整文件导出；加载回归验证首次网络、再次缓存标签，并使用 gzip 运行文件检查响应重建不会损坏内容。报告位于 `reports/diagnostics-v2-*.json` 和 `reports/performance-probe-webkit.json`。
