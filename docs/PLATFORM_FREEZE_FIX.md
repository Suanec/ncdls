# 普通网页运行一段时间后变慢、停绘的修复

版本：20261125.3；日期：2026-11-25。

## 真机证据与根因

用户的 iOS 18.7 / 第 294 关摘要显示约 11 FPS，整帧执行 P95 为 87 ms；页面可见、未暂停、WebGL 未丢失，但停绘 51 次、恢复 50 次。关闭绘制来自旧运行包 `game-93cc5c95db898d1fd1bd.js:154396`。

该位置对应 `src/shared/W.js:22580`。解读模块内字符串表后，这里实际执行的是 `Laya.stage.renderingEnabled = false`。它由对象池维护函数末尾的 `i.j(0)` 进入：旧小游戏平台检查在普通网页来源上进入异常分支，计时器帧数达到 301 后开始额外计算/场景操作，达到 901 后反复关闭绘制。

这解释了先明显掉帧、随后车辆和卡片一起停住，以及刷新后短暂恢复。`.1` 的帧前恢复会被帧内旧检查再次关闭，所以“恢复次数增加”并不代表修复成功。之前的长期测试主要使用 `127.0.0.1`，旧框架对开发地址有特殊处理，遗漏了普通站点条件。

## 修改范围

`build-web.cjs` 对网页版的 W 模块应用 `web-runtime-compat.cjs`，仅移除该平台检查调用。对象池清理、物理、关卡、画质和正常页面隐藏/显示处理保持原逻辑；原始小游戏源码不作该改动。转换要求原调用恰好出现一次，源码变动时构建失败，避免悄悄跳过适配。

音频错误另行处理：原引擎恢复声音时未接住 `AudioContext.resume()` 的拒绝，`Failed to start the audio device` 会被全局异常处理当作加载失败。网页适配在恢复音频的调用点接住同步/异步失败，记录音频警告；下一次点击可重试，不自动刷新或重开关卡，其他运行错误仍照常上报。摘要会显示“音频暂不可用”。

## 验证

- 未修复版本在隔离的 `http://ncdls.test` 上使用本地资源复现：不点击车辆也从约 60 FPS 逐步降至约 22 FPS；第 901 帧后持续停绘，完整调用栈命中同一行。
- 修复后使用普通 HTTPS 来源、手机视口和 DPR 3，实际点击第 2、294 关，自然运行超过 2,000 帧；检查无重复停绘、无需自动恢复，同时验证音频恢复拒绝与后续重试。
- `check-web-runtime.cjs` 执行真实对象池更新函数，确认每帧清理仍然运行、仅平台检查不再调用。既有渲染、对象池、缓存、更新和诊断检查继续运行。
- 浏览器报告见 `reports/platform-freeze-*.json`，可重复执行的浏览器脚本见 `scripts/probe-platform-freeze.cjs`（需要 Playwright 和相应浏览器）。桌面浏览器结果不能当作 iPhone 实测帧率。

这个根因已在本机复现并修正。2026-11-25 用户已在手机上确认“不再卡死，也不卡顿”；后续正式版继续保留该修复。这不表示所有设备都能保持固定 60/120 FPS。

## 更新

通过固定游戏入口或 `recover.html` 升级，在“选择关卡”确认 `20261125.3`。本次修改运行代码，约 9.3 MB 的运行包需要下载一次；未变化的模型和图片复用缓存。无需清空网站数据或存档。更新后回到当前关卡开头。

复测第 294 关时，连续玩一分钟左右；若仍卡住，先不要刷新，复制精简诊断摘要。也可在正常游玩后检测帧率，比较整帧执行耗时和停绘计数。
