# 平台检查：可读学习副本

整理日期：2026-11-26。原文件 `src/shared/W.js`，游戏基准提交 `21800f6 / 20261126.2`。

先读 [platform-guard.readable.js](platform-guard.readable.js)。它把数字地址和临时变量换成具体属性、条件和注释；没有接入游戏，没有改动正在运行的代码。

## 读哪些函数

1. `checkWebLocation()`：读取网页地址，按原来的顺序识别本地地址、发行平台、游戏标识。
2. `checkLicenseCandidates()`：把游戏标识交给授权匹配函数，决定内部检查状态。匹配算法保留为接口。
3. `checkWechatIdentity()`：以微信为例，演示读取 `getAccountInfoSync().miniProgram.appId`。
4. `planLegacyFrame()`：检查状态未设置时，301 帧起创建隐藏模型并增加物理或计算负担，901 帧起关闭绘制。

“隐藏模型”是关闭网格渲染的方块，不是玩家看到的汽车。原代码仍将它加入场景；隐藏不等于没有创建、维护和物理成本。原 `CItem` 还参与后续管理，不能仅据这段代码就认定节点永久不回收。

学习版仅返回动作清单，不真的创建模型、执行空耗循环或停止引擎。

## 运行示例

在工程根目录执行，无需安装依赖：

```sh
node docs/study/platform-guard.readable.js
node docs/study/verify.cjs
```

第一条对比本地地址和 GitHub Pages，在关键帧打印行为；第二条运行原编译模块与可读版的对照实验。均不启动游戏、不联网、不读取存档、不写入源文件。

## 怎样从看不懂的代码读出含义

### 1. 从故障位置缩小范围

先有现场证据：网页可见、WebGL 未丢失，`renderingEnabled` 却被关掉。沿赋值位置追到 `i.j(0)`，再追到初始化检查。没有尝试逐行解释四万多行混淆代码。

原文件的入口和查阅位置：

| 位置 | 作用 |
| --- | --- |
| 18780 | 对象池维护末尾调用 `i.j(0)` |
| 20752 附近 | 内嵌编译模块工厂 |
| 20919 附近 | 从 Base64 恢复内存数据段，起始地址 1024 |
| 21463 附近 | 微信账号信息和 AppID 分支 |
| 21711 附近 | 普通网页来源分支 |
| 22394 附近 | 帧检查及额外场景操作 |
| 22578 附近 | 901 帧后的停绘赋值 |
| 30372 附近 | 授权候选与 `U6` 条目的匹配控制流 |

行号基于本次文件，后续源码变化可能漂移；不要仅凭数字定位。

### 2. 先认出“编译产物”，再读业务

文件里出现 `emscripten::val`、`std::string`、`HEAP32`、`__embind_initialize_bindings`，说明这部分包含 Emscripten/Embind 生成的互操作代码。它用 TypedArray 模拟内存，用句柄引用 JavaScript 对象；不是普通手写业务 JS 的命名习惯。

`a0[(r + 60) >> 2]` 表示按字节地址计算后，访问 32 位整数数组：一个元素占 4 字节，所以右移两位。大量 `h(...)` 则在释放句柄，不能一律看成业务函数调用。

### 3. 把数字地址还原成字符串

原模块将 Base64 字节写到地址 1024 起的位置。按地址找到字节，读取到 `0` 结束，就能取出字符串：

| 地址 | 实际字符串 |
| --- | --- |
| 1858 | `location` |
| 2241 | `href` |
| 2474 | `currFrame` |
| 2658 | `stage` |
| 2751 | `renderingEnabled` |
| 2772 | `appId` |
| 2799 | `getAccountInfoSync` |

`verify.cjs` 开头就有实际解码方法，并会断言这些值与原文件一致。注意有些地址指向已有字符串的中间位置，不能只机械地按零分隔后给字符串编号。

### 4. 找出少数底层函数的真正作用

- `V(输出地址, 对象地址, 属性名地址)` 最终调用的是 JavaScript 属性读取。
- `I2(对象地址, 属性名地址, 布尔值地址)` 最终设置布尔属性。
- `d(字符串, 子串地址, 起点)` 是字符串查找，没找到返回 `-1`。
- `y(undefined)` 返回句柄 `1`；`null / true / false` 对应 `2 / 3 / 4`。

于是下面这些操作串起来，就能认出停绘行为：

```js
const stage = Laya.stage;          // 原来通过地址 2658 取属性
stage.renderingEnabled = false;    // 原来通过地址 2751 写属性
```

还原时特别容易犯两个错：把句柄 `1` 当作布尔真；把保存 `KV` 的私有对象误认成 `window.W`。本次都按桥接函数和实际运行结果核对过。

### 5. 保留分支顺序，不替原代码“优化”规则

原网页判断是对整个 `href` 做区分大小写的子串查找，不是严格的域名白名单。`http://127.0.0.1` 和 `http://localhost` 就可能走不同分支。因此学习版不换成 `new URL(...).hostname`，也不把 `gameId` 自动解码。

原逻辑使用私有 `KV` 标记。初始化后它是 `undefined`；命中某些例外或授权时写入字符串标记。逐帧检查只在 `KV === undefined` 时进入问题分支，并不是简单的 `if (!KV)`。

### 6. 拿原模块做对照，不只相信人工推理

`verify.cjs` 从源文件抽出模块工厂，在独立 Node VM 中运行，用模拟 Laya 对象记录创建模型和停绘操作。对照 42 组场景，包括：

- GitHub Pages、IP 本地地址、localhost、CDN、gameId、4399、mini123、LINE 分支；
- 微信 AppID 例外和普通身份；
- 授权匹配与不匹配两种返回结果；
- 3D/2D/无物理分支，以及关键帧动作；
- `undefined / false / null` 与三个字符串状态标记。

验证所用原文件 SHA-256：`c791c70cee81a717cf489863c9e58f0fe801df65d7f450a9051660566858efa6`。

授权算法 `N0` 在 VM 的内存副本中替换为记录桩，方便检验“传入哪些候选、命中后走什么分支”。这没有验证完整授权算法，也没有改动磁盘上的 `W.js`。物理分支检查的是调用路径，不是真实物理模拟；慢帧和长期停绘的游戏实测另见 [故障记录](../TROUBLESHOOTING.md) 第 7 节及对应 reports。

## 哪些不是完整还原

- 无法恢复作者原变量名、原注释或原 TypeScript 项目；当前命名是为了教学重新命名。
- 没有移植 `N0` 整套授权匹配运算；不传 `matches` 时明确记录“未求值”，不会假装通过。
- 没有展开全部原生平台初始化、徽标函数 `k()`、`CItem` 生命周期及非 HTTP 宿主回调。
- 4399 日期示例限定正常 `YYYYMMDD` 和当前本地时区；未验证无效日期、跨时区和 Unicode 未编码 URL 的所有边界。
- 它不是可以直接替换 `W.js` 的模块。当前游戏继续使用已有浏览器适配，在构建时去掉那一次 `i.j(0)` 调用。
